# KYC Triage Multi-Agent System — Build Explanation

This document walks through **every file** in this project: what it does,
why it's built the way it is, which library was chosen and why, and what
the realistic alternative would have been. It's written for someone who
is comfortable with Python but new to agentic AI frameworks, MCP, and
production LLM-application patterns — the goal is that you could explain
any design decision here in an interview, not just point at the code.

---

## 1. The big picture

The system takes one "applicant" (a simulated ID/utility bill +
optionally an existing customer record) and pushes it through a 5-stage
pipeline to reach **Approve / Reject / Manual Review**:

```
Document Analysis (LLM) → MCP tool calls (deterministic) →
Fraud Detection (LLM) → Compliance Rule Engine (deterministic) →
Compliance Explanation (LLM)
```

The single most important design decision in this whole project, made
early and threaded through everything else, is this:

> **The actual approve/reject/manual-review decision, and every fact that
> feeds a hard-stop rule (watchlist hit, document quality), is computed
> by deterministic Python — never by an LLM.** LLMs are only used for
> synthesis and narrative: turning tool results into a risk score, and
> turning a rule-engine verdict into a human-readable explanation.

Why this matters: a bank's compliance team needs to be able to say
exactly why a decision was made, reproduce it, and audit it. An LLM call
is non-deterministic (even at temperature 0, model updates change
behavior over time) and can't be held to that standard. This is a real,
common pattern in production fraud/compliance systems — "LLM explains,
code decides" — and it's the thing most worth mentioning if an
interviewer asks "why didn't you just let the agent decide?"

Everything below explains how each file supports that architecture.

## 2. `src/mock_data_generator.py` — synthetic data

**What it does:** Generates fake-but-realistic "documents" (a simulated
scanned ID/utility bill) and fake "customer history" (a simulated
existing bank record), bundled into an `ApplicantCase`. It can build four
named scenarios — `clean`, `fraud_mismatch`, `watchlist_hit`,
`incomplete` — so the demo reliably reaches all three final decisions
instead of hoping randomness cooperates.

**Library: `Faker`.** It's the standard Python library for realistic
fake names/addresses/dates/ID-like strings, actively maintained, zero
API cost, fully offline.
*Alternative:* hand-roll random data from hardcoded lists with
`random.choice`. More code, obviously-repeated output, and reinvents
something Faker already does well.

**Why `dataclass`, not Pydantic, for these models?** This data is
generated by our own trusted code, not user input, so we don't need
Pydantic's runtime validation here — we use Pydantic later, at the actual
trust boundary (LLM output), where it earns its keep. `dataclass` gives
named, typed fields with far less boilerplate.

**The seeding trick (`_seed_to_int`):** `Faker.seed()`/`random.seed()`
need an integer, but the UI wants to seed generation from an *uploaded
file's bytes* (so uploading the same file twice gives the same simulated
identity — a nice, honest property for a "simulated OCR" system). A
file's bytes naturally hash to a hex string, not an int, so this function
bridges the gap with SHA-256 (deterministic across runs and processes,
unlike Python's built-in `hash()`, which is randomized per-process for
security reasons).

**A real bug we caught and fixed during testing:** the first version of
the `clean` scenario only aligned the applicant's *name* between the
document and the "on-file" history — date of birth and address were left
to random chance. Under the offline mock LLM this didn't matter (the
mock only checks name matches), but a **real** Gemini/Groq call would
have correctly flagged the random DOB/address mismatches as risk signals
(because the Fraud Agent's prompt explicitly tells it to), potentially
turning a "clean, should-approve" demo scenario into an unwanted manual
review. We caught this by actually running the app in a browser and
reading the live log, not by assuming the code was correct — see
`tests/test_mock_data_generator.py::test_clean_scenario_all_identity_fields_match`
for the regression test that now guards against it.

## 3. `src/guardrails_and_logging.py` — safety and observability

This is the first module everything else imports, because in a real
financial system, safety and observability aren't bolted on afterward.
It does three things:

### 3a. PII redaction

Regex-based detection of emails, phone numbers, SSN/SIN-shaped numbers,
and card-number-shaped sequences, applied both to log output and to any
text about to be sent to a third-party LLM API.

*Why regex, not a library like `presidio-analyzer`?* The fields we need
(emails, phone numbers, ID numbers) are all **pattern-shaped** — regex is
the right tool. If we needed to find "a person's name" in free-flowing
prose (which regex genuinely cannot do reliably), a proper NER-based PII
library would be the correct call instead. Regex is also zero-dependency
and zero cold-start cost, which matters on a shared free HF Spaces CPU.

### 3b. Structured logging + live capture, via `structlog`

Every event is: timestamped, PII-redacted, JSON-rendered to stdout (real
observability — what you'd see in HF Spaces' log viewer or a real
CloudWatch/Datadog pipeline), **and** captured into an in-memory,
per-`run_id` list with a live pub/sub hook.

*Why the pub/sub hook exists:* Streamlit has no supported way to tail its
own process's stdout mid-render. Instead, `subscribe_to_run(run_id,
callback)` lets the orchestrator's background thread push each log event
straight into a `queue.Queue` the moment it happens, which the Streamlit
main thread polls in a loop — that's what makes the "live terminal"
panel genuinely real-time instead of a replay shown only after the whole
pipeline finishes. See `app.py`, section 8, for the consuming side.

*Alternative considered:* buffer logs and display them all at once after
the run completes, or fake "liveness" with `time.sleep()` between lines
of an already-complete log. Both were rejected as dishonest — the
callback approach shows exactly what's happening exactly when it happens.

### 3c. Output validation (`validate_json_output`)

Every agent is instructed to return JSON matching a specific Pydantic
schema. LLMs occasionally wrap JSON in ```` ```json ```` fences, add a
stray sentence, or get a field type wrong. This function is the single
choke point that catches all of that — parse, strip fences if present,
validate against the schema, and **return `None` (never raise) on
failure**, after logging a `guardrail_output_*` event. Every caller
handles the `None` case explicitly (usually: build a safe, escalated
default), which is "fail safe, not silent" — exactly the behavior you
want in a compliance system, and something worth calling out explicitly
as a guardrail pattern in an interview.

### 3d. Prompt-injection guard (`sanitize_for_prompt`)

Text extracted from a "document" is, from the system's point of view,
untrusted input. `sanitize_for_prompt` wraps it in labeled
`<untrusted_document_data>` delimiters (the primary defense — every
agent's instructions explicitly say to treat tagged content as data, not
commands) and logs a warning if it spots obviously suspicious phrases
like "ignore previous instructions" (a secondary, traceability-only
signal, not the actual defense).

## 4. `src/llm_factory.py` — provider selection + offline fallback

**What it does:** `get_model(role)` returns whatever should be passed to
`LlmAgent(model=...)`: a Gemini model-name string, a `"groq/<model>"`
string, or a `MockLlm` instance — decided purely by which environment
variable is set (`GEMINI_API_KEY` → Gemini, else `GROQ_API_KEY` → Groq,
else offline mock).

**Why Gemini is a plain string but Groq needs an extra install
(`google-adk[extensions]`):** `google-adk` has **native, first-class**
support for Gemini — passing a string like `"gemini-2.0-flash"` makes it
call the `google-genai` SDK internally. Every other provider (Groq,
OpenAI, Anthropic, 100+ others) goes through **LiteLLM**, a separate
library ADK optionally depends on. A model string containing a `/`
(`"groq/llama-3.3-70b-versatile"`) is auto-resolved by ADK's model
registry to `LiteLlm(model=...)`, which reads `GROQ_API_KEY` itself
(LiteLLM's own convention).

**Alternative seriously considered and rejected:** hand-write a
`GroqLlm(BaseLlm)` subclass calling the `groq` SDK directly, skipping
LiteLLM entirely (lighter install — no `litellm`/`openai`/`tiktoken`
pulled in). Rejected because it means re-implementing ADK's
request/response translation **and its function-calling (tool-call)
translation** ourselves, and getting that subtly wrong would silently
break tool calls under Groq while looking fine under Gemini — an
unacceptable risk for something billed as "production-ready." We
verified this tradeoff is real by actually installing `google-adk` and
inspecting its live source (see section 11) rather than assuming.

**`MockLlm` — the offline fallback:** A `BaseLlm` subclass that inspects
the prompt text for a few structured signals our agents always embed
(compact JSON) and returns a plausible, schema-valid JSON response via
plain `if` statements — not trying to simulate real language
understanding. This is what keeps the public demo **fully functional**
for a visitor with no API key configured, and it's the reason the
"real decision, not LLM-decided" architecture from section 1 pays off:
because compliance-critical facts never depend on the LLM, mock mode
reaches the same correct approve/reject/manual-review outcome as a real
model would — only the free-text "reasoning" narrative is visibly
labeled `[offline mock]` and simplified.

## 5. `src/mcp_tools_server.py` — a real MCP server

This is the piece that makes "Model Context Protocol" a verifiable claim
rather than a name-drop.

**How it actually runs:** `python -m src.mcp_tools_server` starts an MCP
server speaking the protocol over **stdio** (standard input/output).
`google.adk.tools.mcp_tool.McpToolset` spawns this file as a **child
process** (via `mcp.StdioServerParameters`) and talks real MCP to it —
the same pattern real MCP clients (e.g. Claude Desktop) use for local MCP
servers. There is no shared Python state between the two processes;
every tool call is a real protocol message with real serialization.

**Library: `mcp` (the official Python SDK), `MCPServer` class.** We
initially wrote this against the classic `FastMCP` class from memory,
then **discovered by actually installing the package** that `mcp` 2.x
renamed `FastMCP` → `MCPServer` (`from mcp.server.mcpserver import
MCPServer`) — an object lesson in why we verified every API against the
real installed package instead of trusting training-data memory for a
fast-moving library (see section 11).

**The two tools, and why they're shaped this way:**

- `compare_identity_fields(document, history)` — compares the
  document's name/DOB/address against the on-file history (or reports
  "no history" for a new customer). Name matching uses `difflib.
  SequenceMatcher` (stdlib, no extra dependency) instead of exact string
  equality, because realistic OCR/typo scenarios ("Jon Smith" vs
  "Jonathan Smith") shouldn't produce a false mismatch.
- `check_watchlist_and_flags(history)` — reports watchlist status and
  prior flags, with a simple transparent severity score (watchlist hit
  dominates, each prior flag adds a fixed weight).

**Why these are called *directly by orchestrator.py*, not by the LLM
deciding to call them:** this is the same "code decides safety-critical
facts" principle from section 1, applied to tool-calling specifically.
Checking the watchlist is *mandatory* for every case — it should never
depend on whether an LLM's function-calling logic happened to choose to
invoke that tool. It also elegantly solves the `MockLlm` gap: since
`MockLlm` doesn't support tool-calling at all, letting orchestrator.py
call MCP tools directly means **mock mode gets the exact same real,
deterministic tool results as a real-LLM run** — only the LLM's
downstream reasoning about those results changes.

**Why each tool function is plain Python, not something wrapped up
inside the decorator:** the `@mcp.tool()` decorator registers a function
for the MCP protocol *without* changing what it does when called
directly — so `tests/test_mcp_tools.py` calls `compare_identity_fields()`
and `check_watchlist_and_flags()` as ordinary functions, no subprocess,
no protocol overhead, fast and simple unit tests.

**Why stdio, not HTTP?** MCP supports stdio, SSE, and streamable-HTTP
transports. Stdio needs no port, no network config, and is exactly how
most local MCP servers run in practice. For a multi-tenant production
deployment serving many concurrent users, streamable-HTTP would be the
better choice (one long-lived server instead of one subprocess per
request) — noted in the server's docstring as a one-line extension point.

## 6. `src/agents.py` — the three agents + the rule engine

**Pydantic schemas** (`DocumentAnalysisResult`, `FraudDetectionResult`,
`ComplianceExplanation`) define the exact JSON contract each agent must
return — this is what `validate_json_output` (section 3c) checks
against.

**Why prompt-instructed JSON instead of ADK's native `output_schema`
field?** ADK's `LlmAgent` supports a structured-output mode
(`output_schema=SomeModel`), which is more "native," but many
providers/models can't reliably combine enforced structured output with
tool/function-calling in the same call, and we wanted one uniform
approach that behaves identically across Gemini, Groq, *and* our offline
`MockLlm` (which can't participate in ADK's schema-enforcement machinery
at all). Prompt-instructed JSON + our own guardrail validation is more
portable and, since we validate anyway, no less safe.

**`ComplianceRuleEngine`** — deliberately **plain Python, not an
`LlmAgent`**. It loads `config/rules.yaml` and evaluates hard stops
(watchlist hit → reject; failed document quality → manual review) before
falling through to numeric risk-score bands. This is "policy as code":
a compliance team can read the YAML file and know exactly what the
system will do, in a way they never could with an LLM's judgment call.

**`compute_document_quality_passed`** — similarly deterministic. A
document with low OCR confidence, or an ID-type document with no
expiration date, should never slide through as "approve" purely because
an LLM's free-text opinion said it looked fine.

**The "explanation agent doesn't decide" pattern:** the third agent's
instructions explicitly state the decision has *already* been made and
its only job is to narrate it — and `orchestrator.py` (section 7) then
double-checks the narration doesn't contradict the decision anyway,
because instructions alone are a prompt-level control, not a guarantee.

## 7. `src/orchestrator.py` — the routing orchestrator

This is the file that actually answers "how does the multi-agent system
work end to end."

**Why explicit Python control flow instead of ADK's `SequentialAgent`?**
ADK does offer a graph-based way to chain sub-agents
(`SequentialAgent(sub_agents=[...])`) that automatically passes state
between them. We chose explicit orchestration instead, for two concrete
reasons discovered while designing this:

1. The Compliance stage is a **hybrid** of a deterministic rule engine
   (plain Python, not an agent at all) and an LLM narrative step — that
   doesn't fit cleanly into a pipeline of pure `LlmAgent` nodes.
2. Explicit control flow makes it trivial to emit a clean, ordered
   `stage_started` / `stage_completed` log event around *every* step —
   including the non-LLM ones (the rule engine, the MCP tool calls) —
   for the live terminal panel. `SequentialAgent`'s internal state-passing
   would have hidden that detail rather than exposing it.

**`_run_llm_agent`** — every agent call gets its own fresh
`InMemoryRunner` + session, rather than one long shared conversation.
This costs a little redundant session-setup overhead per call, but keeps
each of the five pipeline stages fully isolated and independently easy
to reason about and log — worth it at this app's scale (a handful of LLM
calls per triage run, not a high-throughput service).

**`_call_mcp_tools`** — spawns the MCP server subprocess once per triage
run, calls both tools, and closes it. A fresh subprocess per run is
simpler and safer than managing one long-lived server across Streamlit's
rerun-the-whole-script execution model, at the cost of ~1-2 seconds of
subprocess-startup latency — an acceptable tradeoff for a demo app.

**`run_triage` vs `run_triage_async`** — everything in this file is
`async` because ADK's `Runner` and the MCP client are both built on
`asyncio`. `run_triage()` is the one bridge point
(`asyncio.run(...)`) between Streamlit's synchronous world and
ADK/MCP's asynchronous world.

**The `run_id` parameter** exists specifically so `app.py` can call
`subscribe_to_run(run_id, callback)` *before* starting the run in a
background thread — otherwise there'd be no way to register a listener
for a run whose ID doesn't exist yet.

## 8. `app/app.py` — the Streamlit UI

**Deliberately contains almost no business logic.** Its only jobs:
collect input, kick off the orchestrator in a background thread, render
the live log as it streams in, and render the final dashboard. Every
actual decision-making happens in files that can be (and are) unit
tested completely independently of Streamlit — a point worth making
explicitly in an interview: the UI is a thin, disposable layer over a
tested core.

**How the "real-time terminal log" actually works, end to end:**

1. `app.py` generates a `run_id` and calls
   `subscribe_to_run(run_id, callback)`, where `callback` just does
   `log_queue.put(event)` — a plain thread-safe `queue.Queue`.
2. It starts a background `threading.Thread` that calls
   `run_triage(case, run_id=run_id)` — this is where the entire
   ADK/MCP/asyncio pipeline runs, on that thread.
3. The **main** Streamlit thread enters a `while True: log_queue.get()`
   loop, re-rendering a single `st.empty()` placeholder with the growing
   log every time a new event arrives, until the worker thread signals
   completion via a sentinel value.

This is what makes the panel genuinely live rather than a fake replay —
each line appears in the UI at the moment the corresponding
`log.info(...)` call actually executes deep inside the orchestrator.

**Why a custom HTML/CSS block instead of `st.code()` for the terminal?**
`st.code()` gives correct monospacing but no color. A small inline
`<div>` with dark background and per-log-level colors (info=blue,
warning=amber, error=red) reads much more like a real ops terminal,
which matters for the "must immediately impress an engineering
interviewer" requirement. All dynamic text inside it is passed through
`html.escape()` first — defense in depth against any HTML injection from
generated content, consistent with the guardrails theme running through
the rest of the project.

**The risk gauge:** `plotly`'s `go.Indicator(mode="gauge+number")` gives
a genuine visual "risk meter" for very little code — chosen over
`st.progress()` (a plain bar, less legible for a 0-100 risk score with
named danger zones) or building a custom SVG gauge (more code for the
same result).

**The privacy banner and upload handling:** the file uploader accepts
any PDF/image, but **its content is never read** — only
`hashlib.sha256(file.getvalue()).hexdigest()` is used, purely to seed the
synthetic identity deterministically. This is stated explicitly in the
UI (not just in code comments) because a public demo that accepts file
uploads has an obligation to be upfront about what happens to them, even
when — especially when — nothing sensitive actually happens to them.

## 9. `config/rules.yaml` — governance as data, not code

This file is the actual source of truth for the compliance decision.
Editing a threshold (e.g., moving the manual-review band from
`risk_score <= 70` to `<= 60`) requires **zero Python changes** — that's
the point of "policy as code": a compliance/governance stakeholder who
doesn't write Python can still read, and in principle propose changes
to, exactly what the system will do.

## 10. `tests/` — 39 tests, all offline

- `test_mock_data_generator.py` — determinism (same seed → same output)
  and per-scenario correctness (including the regression test for the
  DOB/address bug from section 2).
- `test_guardrails.py` — PII redaction, prompt-injection wrapping, and
  every branch of `validate_json_output` (clean JSON, fenced JSON,
  malformed JSON, schema mismatch).
- `test_mcp_tools.py` — the MCP tool functions called **directly**, no
  subprocess, proving the decorator doesn't change their behavior.
- `test_agents.py` — the deterministic rule engine and document-quality
  gate: the two places in the codebase where "correct" has a precise,
  checkable meaning.
- `test_orchestrator.py` — full end-to-end runs of all four scenarios,
  including a **real** MCP subprocess spawn, with `monkeypatch` forcing
  offline mock mode so the suite needs no API key or network access —
  this is what actually proves the whole system holds together, not just
  its individual pieces.

**Why no tests mock out ADK or MCP themselves:** the whole point of the
offline `MockLlm` fallback is that it lets the *real* ADK `Runner`, the
*real* MCP subprocess, and the *real* rule engine all execute for
real in CI, with only the LLM's own API call replaced. That's a
meaningfully stronger integration test than mocking ADK/MCP directly
would have been.

## 11. How the ADK/MCP code was actually validated (not guessed)

Both `google-adk` and `mcp` are young, fast-moving packages — the
`google-adk` API you might remember from a blog post or an earlier
version can differ meaningfully from what `pip install google-adk`
resolves to today (we hit this directly: `mcp` 2.x renamed its `FastMCP`
class to `MCPServer`, with a very clear error message pointing at the
migration guide, when we tried the "classic" import path from memory).

Before writing `agents.py`/`orchestrator.py`/`mcp_tools_server.py`, we:

1. Installed the real packages into a project-local virtual environment.
2. Used Python's `inspect` module to read the **actual, currently
   installed** constructor signatures and field lists for `LlmAgent`,
   `McpToolset`, `StdioConnectionParams`, `BaseLlm`, `LlmResponse`,
   `Runner`, `InMemoryRunner`, and `MCPServer` — rather than trusting
   memory.
3. Wrote small standalone smoke-test scripts that: (a) ran a minimal
   `LlmAgent` backed by a hand-written mock model through
   `InMemoryRunner`, and (b) spawned a real MCP server as a subprocess
   and called its tools through ADK's `McpToolset` — **before** writing
   any of the real application code, to prove the underlying plumbing
   actually works.

This is also why `requirements.txt` pins exact versions: an unpinned
`pip install google-adk` on some future date could silently resolve to a
version with a changed API, breaking a deployed HF Space with no code
change on your end. We additionally verified `requirements.txt` installs
cleanly and passes the full test suite from a **completely fresh**
virtual environment (not just the one accumulated during development)
before considering this project done.

## 12. Summary of alternatives considered and rejected

| Decision | What we did | Alternative considered | Why rejected |
|---|---|---|---|
| Compliance decision | Deterministic rule engine (YAML + Python) | Let an LLM decide approve/reject | Non-deterministic, unauditable — unacceptable for a compliance-critical decision |
| Multi-agent pipeline | Explicit Python orchestration | ADK `SequentialAgent` graph | Compliance stage is a rules+LLM hybrid that doesn't fit a pure LLM-agent pipeline; explicit flow gives full control over per-stage logging |
| Tool invocation | Orchestrator calls MCP tools directly | Let the Fraud Agent's LLM decide whether to call them | Safety-critical checks (watchlist) must be mandatory, not optional; also makes offline mock mode work correctly |
| Groq support | ADK's LiteLLM integration (`google-adk[extensions]`) | Hand-written `GroqLlm(BaseLlm)` calling the `groq` SDK directly | Lighter install, but re-implementing tool-call translation risks silently breaking function calling under Groq only |
| Structured output | Prompt-instructed JSON + Pydantic validation | ADK's native `output_schema` | Needs to work identically across Gemini, Groq, and a from-scratch `MockLlm` that can't participate in ADK's schema machinery |
| Live log delivery | structlog pub/sub → thread-safe queue → polling loop | Buffer-then-replay after the run completes | Replay isn't actually "live" — misrepresents what's happening when |
| PII detection | Regex over pattern-shaped fields | An NER-based library (e.g. `presidio-analyzer`) | Our fields are all pattern-shaped (emails, ID numbers); NER's strength (finding names in prose) isn't the problem we have, and it costs a heavier dependency + cold start |
| Document AI | Fully simulated (Faker, seeded by file hash) | Actually call Google Document AI | Requires a billed GCP project — breaks the zero-cost, credential-free public demo requirement |
